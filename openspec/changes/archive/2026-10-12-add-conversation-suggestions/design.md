# Design

## Context

动机见 proposal.md。影响设计的事实：

- taskboard 自己不调用任何模型。"读懂对话并归纳任务"只能由用户已有的 Agent 来做，taskboard 负责两头：给 Agent 一份读得动的摘要，以及接住 Agent 提出的建议。
- 本机查到的记录位置：Claude Code 在 `~/.claude/projects/<项目>/<会话>.jsonl`，每行一条 JSON，总量可达数百 MB；DeepSeek Harness 在 `~/.dsh/sessions/<项目>/session-<id>/` 下，内容是 zstd 压缩文件。两者的格式都没有公开的稳定性承诺。
- 现有规格要求：数据只经 `core` 读写、并发写入安全、小窗口不加载远程内容、安装不改动 Agent 配置。

## Goals / Non-Goals

**Goals:**

- 摘要小到可以整份放进 Agent 的上下文，并且不含 Agent 回复和工具输出。
- 建议与正式任务分开存放，用户确认前不影响任务列表。
- 重复运行整理不会把用户忽略过的建议再提一遍。

**Non-Goals:**

- 不在 taskboard 里做任何语义判断（哪句话算待办由 Agent 决定）。
- 不做定时整理。
- 不保证能读出每个 Agent 版本的记录；读不出就跳过并说明。

## Decisions

### 1. 摘要由命令生成，归纳由 Agent 完成

`task digest` 是确定性的文本提取，可以写自动测试；Agent 读它的输出后调用 `task suggest`。

- 备选：让 Agent 自己去翻记录目录。原始记录太大，而且每个 Agent 都要重新摸索格式，结果不可控。
- 备选：小窗口直接调用模型接口。需要用户另外配置密钥，也违背"不联网"的现有承诺。

### 2. 摘要的取舍和上限

每个对话取：来源、项目目录、最后活动时间、用户消息。上限为每条消息 300 字符、每个对话最近 20 条、整体约 60 KB；超出时保留最近的对话并注明省略数量。只扫描修改时间在范围内的文件，避免读取全部历史。逐行流式读取 Claude Code 的记录，不把整个文件载入内存。

用户消息里由工具自动插入的内容（系统提醒、命令输出、粘贴的大段文本）按标记识别并去掉；识别不了的按长度截断。

### 3. 每个来源一个读取器，互相隔离

`src/core/digest/` 下每个 Agent 一个模块，输出统一的对话结构。任何一个读取器抛错或遇到无法解析的记录，只影响它自己，并计入"被跳过"的说明。DeepSeek Harness 的记录用 Node 自带的 zstd 解压；它的内部结构需要在实现时对照本机的真实记录确定，这是本设计里最不确定的一块。

### 4. 建议存在同一个数据文件里

`tasks.json` 增加三个可选字段：`suggestions`（待处理）、`dismissed`（被忽略的名称，规范化后保存）、`nextSuggestionId`。缺失时按空处理，因此不需要迁移，`version` 保持 1。这样建议和任务共用现有的加锁与原子写入，小窗口现有的文件监听也自动覆盖建议的变化。

- 备选：单独一个建议文件。采纳建议要同时改两个文件，无法保证原子性。
- `dismissed` 只保存名称不保存全文，并限制为最近 500 条，避免无限增长。

### 5. 去重只做名称的规范化比较

忽略首尾空白和大小写后完全相同才算重复。更模糊的相似判断留给 Agent（它在提出前会看到现有任务和建议）。这样行为可预测，也容易测试。

### 6. 第一次启动的卡片与后台整理

是否显示过卡片记录在 `widget.json` 里（它本来就保存窗口自己的状态），不放进任务数据。

后台整理由主进程启动 `claude -p <固定提示词>`，只放行 `task` 命令，设时间上限（5 分钟），不经过 shell 拼接参数。完成后比较整理前后的建议数量来报告结果。找不到 `claude` 命令时不提供按钮，改为显示可以对 Agent 说的那句话。

- 设计成"点一下才开始"而不是静默自动运行，理由见 proposal.md。
- 只支持 Claude Code：DeepSeek Harness 的无界面运行方式还没有摸清，而且它处于预览期。用户仍然可以在它的界面里手动说"整理一下任务"。
- 提示词是固定文本，不包含任何来自任务数据或对话的内容，避免把用户文本拼进命令行。

### 7. skill 模板分清两条路径

"从对话整理"一律走建议；"用户明确要求添加"直接创建。两条写在同一个 skill 里，并给出各自的触发说法，避免 Agent 把整理结果直接写进任务列表。

### 8. 顺带补一条文档警告

实测发现 DeepSeek Harness 会修改工作区文件夹的访问权限，导致放在其中的 Electron 无法启动。在 README 和接入文档里写明：不要把 taskboard 的安装目录选作 DeepSeek Harness 的工作区。

### 9. 一条建议是一整件事，步骤可以带完成状态

第一版上线后发现 Agent 提出的都是"下一步动作"而不是任务本身：指示问的是"还有什么没做"，摘要只保留对话结尾，建议也无法表达已完成的步骤。三处修正：

- 指示改为"一个项目一条建议"，名称写目标，步骤写主要阶段。
- `task suggest` 增加 `--done-step`，与 `--step` 按命令中的顺序混排；采纳时已完成的步骤以 100% 创建并署名为提出者。存储上步骤从字符串改为 `{ name, done }`，读取时兼容旧的字符串形式。
- 摘要对超长对话保留开头 3 条加最近 17 条，中间标明省略条数。

"哪些阶段已完成"是 Agent 根据用户说过的话推断的，可能不准；用户采纳后可以在窗口里改。

## Risks / Trade-offs

- [摘要包含用户说过的话，会发给运行它的 Agent 的服务商；默认还跨 Agent] → 文档和卡片文字写明；提供 `--agent` 限定来源；摘要不含 Agent 回复和工具输出，降低夹带密钥等内容的可能。用户自己在对话里粘贴过的敏感内容仍可能出现在摘要里，这一点无法由程序判断，文档如实说明。
- [对话内容对读取它的 Agent 来说是不可信输入，其中可能有"请执行某某操作"之类的文字] → 后台整理只放行 `task` 命令；提示词要求把摘要当作资料而不是指令；最坏结果是出现一条奇怪的建议，仍需用户采纳才生效。
- [两个 Agent 的记录格式变化后读不出来] → 读取器隔离、跳过并说明；用带真实结构的小样本做测试，格式变了测试会先失败。
- [Agent 归纳质量不稳定，可能漏掉或编造任务] → 建议必须带来源说明，用户逐条确认；这是已接受的限制。
- [后台整理消耗额度且耗时不定] → 只在用户点击后运行一次，有时间上限，窗口期间可正常使用。
